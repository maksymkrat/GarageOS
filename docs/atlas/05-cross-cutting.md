# 05 · Поперечні аспекти

## Автентифікація та доступ

**Станом на зараз — немає.** Ні контракт, ні клієнт не мають поняття
користувача, токена чи ролі. Режим (сервісний / особистий) обирається
навігацією, а не правами.

Наслідок, який треба тримати в голові: `GET /cars` віддає **всі** авто, а
`GET /my-vehicles` — «мою» техніку без відповіді на питання, хто такий «я».
Щойно з'явиться автентифікація, `my-vehicles` стане залежним від суб'єкта, і
це зміна контракту, а не лише сервера.

Рішення відкладене свідомо: прототип перевіряє доменну модель, не безпеку.
Перед будь-яким розгортанням за межі локальної машини це блокер.

## Формат помилок

Клієнт уже має свій формат — `ApiError` у `src/api/mock/transport.ts`:

```ts
class ApiError extends Error {
  constructor(message: string, readonly endpoint: string, readonly status = 500)
}
```

Три властивості: текст для користувача, ендпойнт для діагностики, HTTP-статус.
Тексти — українською («Авто не знайдено», «Наряд не знайдено»), бо показуються
на екрані як є.

Для `GarageOSWeb` це означає: стандартний ASP.NET `ProblemDetails` **не збігається**
з цією формою. Потрібен або маппінг `ProblemDetails` → `ApiError` у HTTP-клієнті
(рекомендовано: `detail` → `message`, `status` → `status`, `instance` → `endpoint`),
або власний формат відповіді про помилку. Вибір треба зафіксувати ADR, коли
з'явиться HTTP-клієнт.

Статуси, що вже використовуються: `404` (не знайдено), `503` (симуляція збою
транспорту при `FAILURE_RATE > 0`), `500` (дефолт).

## Стани завантаження та збоїв

Кожен екран зобов'язаний обробити три стани — для цього є спільний компонент
`src/components/ui/query-state.tsx`, а `FAILURE_RATE` у мок-транспорті існує
саме щоб ці стани можна було ганяти вручну:

```ts
/** Raise above 0 to exercise the UI's error + retry states against the mocks. */
const FAILURE_RATE = 0;
```

Правило: новий екран із запитом не вважається готовим, поки не перевірений із
`FAILURE_RATE` більшим за нуль.

## Латентність

Мок додає 180–520 ms штучної затримки. Це не декорація, а бюджет: екрани
спроєктовані так, щоб виглядати нормально при такому відгуку. Реальний API,
що стабільно відповідає повільніше, зламає відчуття інтерфейсу — звідси цільове
p95 < 300 ms у [00-overview.md](00-overview.md#якісні-атрибути).

## Незмінність даних

Мок повертає глибоку копію (`JSON.parse(JSON.stringify(...))`), тому екрани
фізично не можуть зіпсувати стор. З реальним HTTP це виконується саме собою,
але інваріант варто пам'ятати: **дані з запиту не мутуються на місці**, нова
версія — через мутацію й інвалідацію ключа.

## Конфігурація

| Що | Де зараз | Куди цільово |
|----|----------|--------------|
| Базова URL API | ніде (моки) | `expo-constants` + `app.json` → `extra` |
| Рівні логування сервера | `GarageOSWeb/GarageOS.Api/appsettings.json` | без змін |
| Секрети | немає | змінні середовища, не в репо (`.gitignore` уже закриває `.env`, `appsettings.Local.json`) |

## Логування та діагностика

Сервер — дефолтний `Microsoft.Extensions.Logging` із шаблону
(`Default: Information`, `Microsoft.AspNetCore: Warning`). Структурованого
логування, кореляційних ідентифікаторів і трейсингу ще немає.

Мінімум, який варто додати разом із першим реальним ендпойнтом: кореляційний
`X-Request-Id`, що проходить від клієнта в лог сервера — бо `ApiError.endpoint`
уже дає половину зв'язку, але без ідентифікатора запиту не склеїти конкретний
збій на екрані з рядком у логу.

## Тести

**Немає жодного** — ні на клієнті, ні на сервері.

Пропорція, що має сенс для цієї системи:
- **Сервер:** тести на інваріанти з
  [03-data-model.md](03-data-model.md#інваріанти-які-нині-тримає-тільки-мок) —
  нормалізація номера й телефону, дефолти, статус при створенні, 404 на
  осиротілий наряд. Це саме те, що нині тримає тільки мок і що легко загубити.
- **Контракт:** перевірка, що відповіді сервера збігаються за формою з
  `domain.ts`. Найцінніший тест у проєкті, бо шов транспорту — єдине місце,
  де клієнт і сервер можуть розійтися непомітно.
- **Клієнт:** стани `query-state` і композиція `useWorkBoard`.
