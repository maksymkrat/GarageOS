# ADR-0024 · Рядок наряду отримує `id` і власний шлях; наряд більше не переписується цілком

**Статус:** Accepted · **Дата:** 2026-10-22 · **Ухвалено:** 2026-10-22

## Контекст

[ADR-0022](0022-order-crud-and-service-authorization.md) зробив `PUT /orders/{id}`
повною заміною наряду — і зробив це з конкретної причини: рядки не мали `id` у
контракті, тож вхідний рядок **нема з чим зіставити**. «Та сама робота з новою
ціною» і «інша робота замість неї» виглядали однаково, і єдина чесна відповідь
була — не зіставляти, а замінювати все.

Ціна цього рішення була названа там же й виявилася відчутною на практиці:

- щоб виправити одну ціну, клієнт надсилав увесь наряд;
- `order_works.id` і `created_at` мінялися при кожному збереженні;
- інтерфейс мусив бути однією великою формою, де роботи й деталі правляться
  разом, бо окремо їх не існувало.

[03-data-model](../03-data-model.md) тримав цей вибір відкритим прямим текстом:
«або лишити їх як JSON-колонку, або нормалізувати й додати `id` — тоді
зміниться контракт клієнта».

## Рішення

**Рядки отримують `id` у контракті.** У базі він був завжди — `order_works` і
`order_parts` нормалізовані з першої міграції, — ховав його лише DTO. Тож це
зміна контракту й **жодної міграції**.

```ts
export interface OrderWork {
  id: number;
  description: string;
  price: number;
  paymentStatus: PaymentStatus;
}
```

**Вхід і вихід розходяться.** `OrderWorkInput` і `OrderPartInput` не несуть
`id`: рядок, який пишуть, названий шляхом, а новий рядок `id` ще не має. Це та
сама межа, що в [ADR-0021](0021-edit-and-delete-in-my-garage.md), і вона
скасовує протилежне рішення ADR-0022, де типи рядків були спільні для обох
напрямків — бо тоді вони були значеннями без ідентичності, а тепер це сутності.

**Шість нових ендпойнтів, по три на кожен вид рядка:**

```
POST   /orders/{id}/works            PUT /orders/{id}/works/{workId}      DELETE …
POST   /orders/{id}/parts            PUT /orders/{id}/parts/{partId}      DELETE …
```

Сегмент зветься `works` і `parts` — так само, як поля в `Order`
([ADR-0002](0002-client-contract-source-of-truth.md)).

**`PUT /orders/{id}` звузився до скарги.** Тіло — `{ description }`, і більше
нічого: рядки тепер мають власні адреси, тож їм нема чого робити в тілі наряду.
Повна заміна з ADR-0022 **скасована**.

**Рядок знаходиться разом зі своїм нарядом.**

```csharp
db.OrderWorks.FirstOrDefaultAsync(x => x.Id == workId && x.OrderId == orderId, ct);
```

Рядок чужого наряду читається як «немає» — той самий `404`, що й для чужої
техніки в [ADR-0019](0019-create-my-vehicle.md). Інакше `/orders/5/works/7`
правив би рядок наряду 6, якщо вгадати `id`.

## Наслідки

**Ідентифікатори рядків перестали «текти».** Наслідок ADR-0022 — «`order_works.id`
інші після кожного збереження» — більше не діє: правка рядка торкається одного
рядка. На цих `id` тепер можна будувати, зокрема ключі списків у React: на
екрані наряду `key={work.id}` замінив індекс, який я ж туди й поставив, коли
ідентичності не було.

**Наряд редагується у трьох різних місцях, і це навмисно.** Екран «Змінити
наряд» відповідає лише за скаргу й за видалення наряду; робота й деталь мають
власні екрани, які відкриваються дотиком по рядку. Нова робота й нова деталь
додаються кнопками просто в картках наряду, а не всередині форми.

**Форма створення наряду лишилася спільною.** `POST /orders` і далі приймає
масиви рядків: заводити порожній наряд, щоб потім додати три рядки трьома
запитами, було б гірше для тієї єдиної ситуації, де наряд народжується цілим.

**Кожна правка рядка перечитує чотири кеші.** Ціна роботи й стан оплати — це
гроші, а борг і фінанси обчислювані
([ADR-0011](0011-debt-derived-from-orders.md)), тож `invalidateOrderWorld`
викликається і для рядків, не лише для наряду.

**Двадцять п'ять ендпойнтів замість дев'ятнадцяти.** Поверхня API зросла
відчутно, і це свідома плата: дрібна операція коштує дрібного запиту, а не
перезапису цілої сутності.

**Валідації на сервері як не було, так і немає.** `OrderWorkRequest` прийме
від'ємну ціну, `OrderPartRequest` — продаж, менший за закупку. Межі тримає
форма.
